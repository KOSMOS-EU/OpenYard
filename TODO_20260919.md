## [ ] NAME-Kollision: Systemfeld vs. Client-Metadatum

### Problem

`mapResourceInfo` mischt Systemfelder und Client-Metadaten flach
in ein JSON-Objekt:

```json
{
  "name": "Rechnung_LCS.pdf",     ← Systemfeld (Dateiname)
  "NAME": "LCS Computer Service",  ← Client-Metadatum (Anrede/Firma)
  "id": "base64...",
  "type": "file",
  "size": 29912,
  "MAND": "5530",
  "BELEG_NR": "RE-2026-001"
}
```

Weil `ToClientKey("ctrl.name")` → `NAME` ergibt und das Systemfeld
`name` (lowercase) heisst, funktioniert es aktuell zufaellig durch
Case-Sensitivitaet. Aber:

- JSON-Keys sind case-sensitive, manche Clients behandeln sie aber
  case-insensitive (z.B. .NET JsonConvert mit DefaultSettings)
- Weitere Kollisionen moeglich: `type`/`TYPE`, `status`/`STATUS`,
  `path`/`PATH`, `size`/`SIZE`

### Betroffene Systemfelder (mapResourceInfo)

```
id, name, path, modified, etag, type, size, mimeType, parentId
```

Wenn ein Client-Metadatum den gleichen Namen hat (case-insensitive),
ueberschreibt es das Systemfeld oder umgekehrt.

### Loesung

Client-Metadaten in ein eigenes Sub-Objekt verschieben:

```json
{
  "name": "Rechnung_LCS.pdf",
  "type": "file",
  "size": 29912,
  "metadata": {
    "NAME": "LCS Computer Service",
    "MAND": "5530",
    "BELEG_NR": "RE-2026-001"
  },
  "system": {
    "oy.subject": "Rechnung LCS",
    "oy.creatorName": "Kroeber"
  },
  "enriched": {
    "doc.type": "rechnung",
    "amounts.total": "892.50",
    "sender.company": "LCS GmbH"
  }
}
```

### Aufwand

- mapResourceInfo aendern (mapping.go)
- Alle Clients anpassen die Metadaten aus dem flachen Objekt lesen
- Tests anpassen
- Rueckwaertskompatibilitaet: Query-Parameter `?flat=true` fuer alte Clients

### Prioritaet

Mittel. Aktuell funktioniert es durch Case-Sensitivitaet, aber fragil.
Wird relevant wenn weitere Fachverfahren mit generischen Feldnamen
(NAME, STATUS, TYPE) dazukommen.
